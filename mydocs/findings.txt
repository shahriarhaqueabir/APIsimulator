Key Technical Mechanics
GDPR Dual-Header Audit Mechanism — every API call requires two custom headers:

LMG-Data-Privacy-Access-Principal — who is accessing the data (e.g. backend-erika.mustermann%40example.com or nobody for non-personal calls)
LMG-Data-Privacy-Access-Justification — why (e.g. open_account, onboarding.identity_verification)

This creates an auditable access log for every personal data access, baked into every single API call. Not optional. This is the compliance layer partners must implement correctly or access fails.
Idempotency — full IETF-draft-standard implementation on POST /orders. Key behaviours:

Key max 100 chars, UUID recommended
24-hour expiry window
Same key + different payload → 422 immediately
Failed validation requests don't consume the key
Currently only on order creation; explicitly scoped to extend to other write ops

Webhooks — signature-validated via HMAC-SHA256 with LMG-Signature header format t=<epoch>,v1=<hex>. Replay attack protection via timestamp check. Webhook listeners must return 200 within 10 seconds or risk retries. Events are notifications, not data sources — the pattern is: receive event → fetch current entity state from API → update mirror.
Data Mirroring pattern (June 2026 doc) — full architectural guide published specifically for integration partners. Covers: event queue design, idempotency, DLQ, reconciliation, out-of-order handling. API is always the authoritative source of truth — this is stated explicitly and repeatedly. Integration partners are expected to build shadow-copy mirror systems.
Workflows (Savings Plans) — creates recurring investment instructions (order.create_and_confirm action + schedule trigger). Currently only monthly cadence in production (daily available in sandbox). Workflows are immutable — change = cancel + recreate. Workflows are confirmed separately from orders they generate; at cut-off time the order is created, at execution time it settles. Cancel after cut-off = must cancel workflow AND the generated order separately.
Account onboarding flow (full sequence in docs):

Fetch agreements (GET /agreements) → present legal docs to user
Collect user data
Create account (POST /accounts) → returns account ID in created status
Check onboarding blockers (GET /accounts/:id/checks) → typically experience and identity_verification both need action
Start video identification (POST /accounts/:id/identity_verification) → get redirect URL to WebID
Set experience profile (POST /accounts/:id/experience) → knowledge/experience survey
Wait for account.created webhook event or poll /checks

Business accounts (Dec 2024) — separate entity model. Requires beneficial owners, legal representatives, document submission. Separate endpoint group /businesses.
Treasury module — mandates, transfers, financial reporting, and a fee breakdown system allowing partners to see per-customer contributions to aggregated treasury fees.
Income Distributions — dividend/distribution tracking per instrument.

Interview-Relevant Observations
What a Solutions Engineer would actually touch: The onboarding flow, GDPR headers on every call, webhook implementation, idempotency on orders, and potentially the Treasury/Income Distribution reporting endpoints depending on partner type.
Where integration pain lives: The GDPR dual-header requirement is non-trivial for partners to implement correctly — every call needs a meaningful principal + justification that creates a real audit trail. The Data Mirroring doc shows lemon.markets has invested significantly in telling partners how to build robust integration layers, which implies they've seen partners get it wrong.
Product direction visible in changelog: The arc is clear — individual account → business accounts (Dec 2024) → self-service personal data updates (Oct 2025) → tax residency updates (Jan 2026). They're moving toward a more complete lifecycle management product, not just order placement.
What's explicitly sandbox-only: Daily workflow cadence, test ISINs for trading halts and yield scenarios (specific XF00000000XX ISINs documented), WebID test flows.
One gap: The sidebar has pages (Authorization, Portfolio Performance, Strong Customer Authentication) not indexed in llms.txt — meaning they were either added after the index was last generated or excluded intentionally. Worth knowing these exist if you're demoing the docs.
